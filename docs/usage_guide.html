Questrel — Comprehensive Usage Guide

Overview

Questrel generates small branching "plays" (quests) from a database of templates, graphs, and resource pools. The output is structured data suitable for a game engine.

Key Concepts

  • Template: a reusable quest/play blueprint
  • Graph: nodes + edges representing the branching script
  • Resources: characters, locations, props used to fill the template
  • Pools: curated subsets of resources with weights and optional conditions
  • State: runtime flags that influence branching and pool availability

Database Backends

The MVP uses SQLite via async SQLAlchemy. Postgres can be adopted later by switching the DB URL and migrating JSON TEXT columns to JSONB. Constraints/metadata/spec fields are stored as JSON in TEXT behind a stable Python type facade.

Scenario 1 — Quick Demo (CLI)

This is the fastest way to see Questrel generating different plays.

Option A: One-shot demo (seed + multiple generations)


H:/Documents/dev/git_repos/Questrel/.venv/Scripts/python.exe questrel_demo.py demo \
  --db sqlite+aiosqlite:///./questrel_demo.db \
  --overwrite \
  --runs 6 --start-seed 1 \
  --flag allow=true --flag brave=true --flag has_key=true --flag magic=true

By default it prints one summary line per run. Add --json to print full JSON for each run.

Option B: Manual steps

Step 1: Seed a demo SQLite DB


H:/Documents/dev/git_repos/Questrel/.venv/Scripts/python.exe questrel_demo.py seed --db sqlite+aiosqlite:///./questrel_demo.db --overwrite

Step 2: Generate a play

Flags control branching conditions and pool item availability. Missing flags evaluate as None. 


H:/Documents/dev/git_repos/Questrel/.venv/Scripts/python.exe questrel_demo.py generate \
  --db sqlite+aiosqlite:///./questrel_demo.db \
  --max-characters 3 --locations 2 --props 1 \
  --seed 1 \
  --flag allow=true --flag brave=true --flag has_key=true --flag magic=false

Step 3: Generate again with a different seed

Different seeds can select different templates and produce different bindings while remaining deterministic. 


H:/Documents/dev/git_repos/Questrel/.venv/Scripts/python.exe questrel_demo.py generate \
  --db sqlite+aiosqlite:///./questrel_demo.db \
  --max-characters 3 --locations 2 --props 1 \
  --seed 2 \
  --flag allow=true --flag brave=true --flag has_key=true --flag magic=true

Scenario 2 — Using the Library from Python

You can integrate Questrel directly in a game server. This example creates a request and calls generate_play_from_url. 


import asyncio

from questrel import GenerationRequest, State, generate_play_from_url

async def run():
    req = GenerationRequest(max_characters=3, location_count=2, prop_count=1, seed=42)
    state = State(flags={"allow": True, "brave": False, "has_key": True, "magic": True})
    gen = await generate_play_from_url("sqlite+aiosqlite:///./questrel_demo.db", req, state=state)
    print(gen.model_dump_json())

asyncio.run(run())

Scenario 3 — Using an Existing AsyncSession (Server Integration)

If your application already has an async SQLAlchemy engine/session (for example, a web server), call generate_play(session, ...) directly. 


from sqlalchemy.ext.asyncio import AsyncSession

from questrel import GenerationRequest, State, generate_play

async def handle_request(session: AsyncSession) -> str:
  req = GenerationRequest(max_characters=3, location_count=2, prop_count=1, seed=7)
  state = State(flags={"brave": True})
  gen = await generate_play(session, req, state=state)
  return gen.model_dump_json()

Scenario 4 — Populating the Database (Template + Graph + Pools)

The demo seeding is implemented in code (see src/questrel/seed/demo_seed.py), but the same concepts apply when you build your own content pipeline.

Step-by-step

  1. Create a play_template row (id, key, name).
  2. Create requirements: role requirements, location requirements, prop requirements.
  3. Create script_node rows (start node, scenes, endings).
  4. Create condition_expression rows for your branching rules using the DSL.
  5. Create script_edge rows linking nodes:
    • Set priority (higher wins).
    • Set order_index (author order).
    • Set weight for weighted selection among SINGLE edges.
    • Set selection_mode per edge: single or multi.
  6. Create catalog resources (character_resource, location_resource, prop_resource).
  7. Create pools (resource_pool) and pool items (kind-specific tables) with weights.
  8. (Optional) Gate pool items using condition_expression references.

Condition DSL Reference

The DSL is intentionally restrictive for safety. It supports only state.flags["x"] lookups, literals, boolean operators, and comparisons. 


state.flags["reputation"] >= 10
state.flags["has_key"] == True
state.flags["faction"] in ["mages", "thieves"]
state.flags["unknown"] == None

Logging

Questrel can log to a file. The demo CLI supports --log-file, --log-level, and --no-log. In a game integration you can call questrel.logging.configure_logging().

Troubleshooting

  • If generation fails with "not enough candidates", add more pool items or relax constraints.
  • If branching doesn't trigger, check your state flags and condition expressions.
  • If you need reproducibility, always provide a seed.

Scenario 5 — Switching to Postgres (Future Migration)

Questrel is written to be SQLite-first but Postgres-ready. When you are ready to move to Postgres, you typically:

  1. Create a Postgres database and choose an async URL, for example: postgresql+asyncpg://user:pass@host:5432/db.
  2. Install asyncpg in your environment.
  3. Run Alembic migrations against the Postgres URL.
  4. Migrate JSON TEXT columns to JSONB (recommended) and add indexes as needed.
  5. Update your app configuration to use the new DB URL.
